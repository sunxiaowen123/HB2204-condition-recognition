# HB2204 Tractor Load-Condition Recognition for Hybrid Powertrain EMS

Physics-constrained, unsupervised **working-condition recognition** for a **series-hybrid tractor**, designed as the perception front-end of an energy-management strategy (EMS). It runs on real field-tillage data from a **HB2204 (220 hp)** tractor plowing hard soil in Altay, Xinjiang (4-furrow plough, 30 cm depth), acquired with an HBM six-component load cell at **200 Hz** over seven consecutive passes on the same field.

The pipeline produces unannotated per-window condition labels via a **hierarchical, physics-constrained Gaussian mixture model (PC-GMM)**, benchmarks six model families, and evaluates a **low-cost CAN-only signal set + INT8-quantized edge deployment**.

## Highlights

- **Real field data, not synthetic.** Seven passes from one machine and one field, with heavy measurement noise and a small fraction of windows in transition between ploughing and headland maneuvers.
- **Physics-constrained pseudo-labelling.** A hierarchical PC-GMM respects the physical structure (idle/headland/ploughing separated by speed and draft force; the two ploughing grades are an ordinal median split, not natural clusters — stated honestly).
- **Two feature sets.** `CAN-only` (19 dims, available on a production tractor without the expensive six-component sensor) and `Full` (31 dims, incl. six-component draft force `Fx`, the scientific upper bound). Powertrain "effect-side" quantities (generator/motor/battery power, SOC) are used **only for posterior physical validation, never as features** — label leakage is avoided by construction.
- **Honest findings.** `Fx` is decisive; wheel-slip adds a mild gain; frequency-domain features and deep models (LSTM/TCN) add **no** gain over gradient boosting in this small-sample regime (a negative result that favors cheap deployment).

## Condition classes (5, established after data audit)

| Code | Condition | Unsupervised criterion |
|---|---|---|
| 0 | Idle/Stop | vehicle speed ≈ 0 |
| 1 | Headland / light maneuver | low draft force, non-zero speed |
| 2 | Transition (implement engage/disengage) | GMM posterior mixing / adjacent-window `Fx` jump > 4 kN |
| 3 | MedHeavy ploughing | lower half of the ploughing-mode `Fx` range |
| 4 | Heavy ploughing | upper half of the ploughing-mode `Fx` range |

Honest caveat: idle/headland/transition/ploughing are structures the GMM finds naturally; the MedHeavy/Heavy split is an **ordinal median binning** on the single ploughing-mode `Fx` peak (no stable "medium-load ploughing" cluster exists at fixed depth — only ≈2.7% of windows fall in 15–27 kN).

## Reproduce

Run the steps in order (each writes into `cache/`, `results/`, `main_text/`, `supplementary/`):

```bash
cd src
python step1_build_windows.py          # windowing (3 s, 50% overlap)
python step2_pc_gmm.py                 # hierarchical PC-GMM pseudo-labels
python step3_features.py               # feature engineering (CAN-only / Full)
python step4_loso_classical.py         # RF / SVM-RBF / XGBoost / MLP, LOSO-CV
python step5_loso_deep.py              # LSTM / TCN (slowest)
python step6_ablation.py               # progressive feature ablation + slip wheel-position
python step7_confusion_compare.py      # model comparison + main-model confusion matrix
python step8_pca.py                    # PCA mechanism analysis
python step9_posthoc.py                # powertrain-power posterior validation
python step10_int8.py                  # INT8 static quantization + edge deployment
python step11_signal_equivalence.py    # CAN/GPS signal equivalence
python step12_figure1.py               # research-framework flowchart
python step13_segment_summary.py       # per-segment summary table
python step14_spectral_basis.py        # frequency-domain bandwidth justification
python step15_clustering_baseline.py   # KMeans / unconstrained GMM vs PC-GMM
python step16_pcgmm_sensitivity.py     # PC-GMM tau/delta sensitivity
python step17_significance.py          # McNemar + fold-level paired tests
python step18_field_layout.py          # field-track map
python step19_deep_multiseed.py        # deep-model robustness across seeds
```

On Windows you can also run `.\reproduce.ps1` from the repo root to execute the core steps 1–12 sequentially.

**Validation protocol.** A **leave-one-segment-out (LOSO)** scheme with seven folds (one pass held out per fold) is used so that reported performance reflects generalization to an unseen pass. Imputation, standardization and class weights are estimated strictly within each fold. Fold-level macro-F1 is reported as mean ± std; pairwise model significance uses McNemar's test on out-of-fold predictions with paired fold-level Wilcoxon tests as the conservative reference (overlapping windows are not fully independent, so the fold-level tests are the primary evidence).

## Results (honest summary)

1. Full-signal upper bound XGBoost/RF: **Acc ≈ 0.973, macro-F1 ≈ 0.920**; steady four classes recall 97–99%, transition recall ≈ 65% (the dominant error).
2. CAN-only best macro-F1 ≈ **0.76**; the bottleneck is separating MedHeavy ↔ Heavy without `Fx`.
3. `Fx` is the decisive feature (**+0.157 macro-F1**); wheel slip adds a mild gain, and front-wheel slip is as effective as rear-wheel slip.
4. Frequency-domain features add no gain; deep models (LSTM/TCN) do not beat XGBoost at this sample size (negative result → cheap deployment).
5. After controlling vehicle speed, heavy-load `Fx`/power are consistently higher; series powertrain power balance r ≈ 0.996.
6. INT8 small MLP: **≈ 11 KB, ≈ 81 µs/window**, CAN features macro-F1 ≈ 0.757 (quantization-lossless).

A physics-based threshold rule achieves ≈ 97.9% agreement with the reference labeling, versus PC-GMM's ≈ 97.0% — the paper positions PC-GMM's value not as a raw accuracy gain but as **automatic recovery of physically ordered grades without manual threshold calibration** (see the manuscript's Methods/Results for the exact framing).

## Data

The seven `plowing_*_processed.csv` files are the pre-processed acquisition passes at 200 Hz. Channel names follow `config.py`: `t_s, source_segment, Fx1, Fx3, Fx_left_sum, GnssSpeed_kmh, GnssSpeed_mps, WhlBasVehSpd_kmh, WhlBasVehSpd_mps, v_LF, v_LR, v_RR, Slip_LF, Slip_LR, Slip_RR, P_gen_kW, P_mot_kW, P_bat_kW, SOC, power_err_flag`. Soil moisture was not measured in this campaign and is listed as a limitation in the manuscript.

## Git LFS

The raw data in `data/` (7 × ~10–58 MB CSV plus the field-track `.mat`, ≈ 245 MB total) are tracked with **Git Large File Storage (LFS)** via `.gitattributes`, so they stay out of the git object database and keep clones lean.

Before pushing, on your machine (once):

```bash
git lfs install            # register the LFS filters
git init
git add .gitattributes     # must be staged BEFORE the large files so LFS applies
git add .
git commit -m "initial release"
git branch -M main
git remote add origin <your-repo-url>
git push -u origin main
```

Use a repo on a host that supports LFS (GitHub/GitLab free tiers do). See `PUSH_TO_GITHUB.md` for the full step-by-step.
